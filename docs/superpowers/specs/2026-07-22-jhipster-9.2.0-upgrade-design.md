# JHipster 9.2.0 Upgrade Design

## Goal

Upgrade the MiniBlog backend from JHipster 9.1.0 to exactly JHipster 9.2.0 while retaining its project-specific behavior and using JHipster's supported automatic upgrade workflow before any fallback.

## Current State

- The repository is clean on `master` and already has a `jhipster_upgrade` branch and the standard reference/upgrade merge history.
- `.yo-rc.json` and `package.json` identify JHipster 9.1.0 as the current generated version.
- The application is a Maven-built Java 21 microservice with PostgreSQL, JWT authentication, no generated client, and three generated entities.
- The checked-out `node_modules` contains a stale JHipster 9.0.0 installation, so it must not select the generator version used for this upgrade.
- Project-specific security and password-handling changes must be preserved when generator changes overlap them.

## Chosen Approach

Run the official automatic upgrade sub-generator from an exact ephemeral package version:

```text
npx generator-jhipster@9.2.0 upgrade
```

This pins the generator to 9.2.0 instead of relying on either the stale local installation or the moving `latest` tag. The sub-generator may update its dedicated `jhipster_upgrade` branch, create its normal generated commits, and merge the generated result back into `master`.

The repository and toolchain meet the relevant preconditions: Git is initialized, the working tree is clean, Java 21 is installed, and Node 24.15.0 with npm 11.12.1 satisfies JHipster 9.2.0's generator engine requirement of Node `^22.18.0 || >=24.11.0` and npm `>=10.0.0`.

## Conflict and Failure Handling

Merge conflicts are part of the supported upgrade workflow. Resolve them by combining JHipster 9.2.0's generated changes with the application's intentional custom behavior. In particular, preserve the custom password encoding and DTO serialization protections while accepting compatible generated security hardening.

Do not use `--skip-checks` initially. If the automatic upgrader fails, diagnose the failure and retry only when the remedy remains within the automatic workflow. Manual regeneration is the fallback only when the automatic sub-generator cannot complete; it must use JHipster 9.2.0 and the committed `.yo-rc.json` and `.jhipster` metadata.

## Expected Upgrade Surface

Accept generator-owned changes required by JHipster 9.2.0, including:

- `.yo-rc.json`, `package.json`, `package-lock.json`, and README version references;
- Maven parent, JHipster framework, plugins, wrapper, and dependency versions;
- generated Java configuration, security, REST, and test code;
- Docker Compose and monitoring definitions;
- development-container settings, including JHipster 9.2.0's generated Node tooling baseline.

Avoid unrelated refactoring or feature work. Entity definitions and application behavior remain unchanged except where JHipster 9.2.0 intentionally changes generated behavior or hardening.

## Verification

After conflict resolution and dependency installation:

1. Confirm the repository is no longer in a conflicted merge state.
2. Confirm `.yo-rc.json` and `package.json` use `9.2.0`, the lockfile resolves `generator-jhipster` 9.2.0, and no generated documentation still identifies 9.1.0 as the application version.
3. Review the complete diff and commit graph for accidental deletion of project-specific code.
4. Run `npm run ci:backend:test`, which covers Maven/toolchain information, Javadocs, checkstyle, and the backend verification suite.
5. Run any narrower tests needed to diagnose failures, then rerun the complete backend CI test command before declaring the upgrade complete.

## Success Criteria

- The generated application metadata identifies JHipster 9.2.0 exactly.
- The automatic JHipster upgrade workflow completes, or a documented automatic-workflow failure justifies the pinned manual fallback.
- Custom security and password-handling behavior remains present.
- The full backend CI test command passes.
- The final working tree contains only upgrade-related changes and is free of unresolved conflicts.
